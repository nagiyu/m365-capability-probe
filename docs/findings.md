# 所見

このプローブを実テナントに対して走らせて出てきたものと、それぞれがツールを変えるに足る理由。

**これらは観測であって、仕様の説明ではありません。** 出所は 1 つの Microsoft 365 テナント、1 つの
アプリ登録、1 つのサイト、共有状態の違う 4 つのファイルで、日付は 2026-08-03 / 04 です。
1 つのテナントは 1 つのテナントでしかありません。頼りにする前に、ご自身のテナントに対して走らせて
ください。以下のテナント名・サイト名・アカウント名・各種 ID は伏せ字に置き換えてあります。

**8 つの所見と、事前の予測との関係はそれぞれ違います。**

| | 予測 | 結果 |
| --- | --- | --- |
| 所見 1〜3 | 立てた | **裏切られた** |
| 所見 4 | 立てた (`404` だろう) | **当たった** ― ただし当たったこと自体が所見だった |
| 所見 5・6 | **立てていない** | 立てられなかったので測った |
| 所見 5 の追試 1〜4 | **立てていない** | 詳細は所見 5。**追試 4 は、追試 2 の結論が広すぎたことを示した** |
| 所見 6 の追試 1〜4 | **立てていない** | **追試 3 は、所見 6 そのものが広すぎたことを示した** |

**広すぎた結論が、これまでに 2 つ出ています。** どちらもそのときの測定は正しく、
**そこから一般化した部分だけ**が間違っていました ― 所見 5 の追試 2 (「権限は変数ではない」) と、
所見 6 の本文 (「一覧はできるが中身は見せない」)。訂正は消さずに、当該箇所に残してあります。

**2 つとも原因は同じです。変数を 1 つしか動かさずに、全体について語ったこと。** 前者はトークンが
1 種類しかなく、後者は測ったグループが 1 つでした。

所見 4 が示しているのは「`404` が返る」ことではなく、**その `404` がパスの書き間違いと区別できない**
ことです。予測が当たっても、その含意までは見えていませんでした。

全体を通じて、区別しておく価値のあるものが 1 つあります。**測定したこと** と **それを説明する読み**
は別物です。測定は再現できます。説明は測定に最もよく合う読みであり、機構を確認していない箇所は
その旨を明記しています。

## 観測を生んだ設定

環境の全体像は [docs/environment.md](environment.md) にあります。ここには所見に直接効く部分だけを
再掲します。

アプリ登録は 1 つ。管理者の同意を与えたのは、正確に次のものだけです。

| API | アクセス許可 | 種類 |
| --- | --- | --- |
| Microsoft Graph | `Sites.Read.All` | アプリケーション |
| Microsoft Graph | `Sites.Read.All` | 委任 |
| Microsoft Graph | `User.Read` | 委任 |
| SharePoint | `Sites.Read.All` | アプリケーション |

これ以外は何もありません。特に **SharePoint の委任アクセス許可は 1 つもなく、Azure Rights Management
には何も付与していません** ― この 2 つの欠落が、所見 1 と所見 2 の主題です。

資格情報は **クライアント シークレットと、自己署名証明書 1 つ**。証明書は 2026-08-04 に登録しました。
**アクセス許可は証明書を足しても 1 つも変わっていません** ― 変わったのは、アプリが自分を証明する
方法の選択肢が 2 つになったことだけです。所見 5 の追試 3 は、この 2 つを同じ実行の中で並べたものです。

「パブリック クライアント フローを許可する」は有効 (デバイス コード用)。委任側でサインインする人物は
テスト用サイトの **閲覧者** であり、管理者ロールもディレクトリ ロールも持ちません。ファイルは共有状態を
変えた 4 つで、うち 1 つは継承を切ったサブフォルダの中にあります (内訳は
[environment.md](environment.md))。

各サブコマンドは複数回実行しています。観測のための実行と、ツールを直したあとに同じ値が出ることを
確かめる実行の両方です。数字の再現については後段の「再現性」を参照してください。

## 所見 1 ― Microsoft Graph への同意が SharePoint に届く

### 予測

このアプリに SharePoint の **委任** アクセス許可はない。したがって SharePoint リソースへの委任
トークン要求は、Azure RMS のそれと同じように拒否されるはずである。

### 観測

成功する。しかも本物のトークンが返る。

| | 値 |
| --- | --- |
| `aud` | `00000003-0000-0ff1-ce00-000000000000` |
| `scp` | `Sites.Read.All User.Read` |

`00000003-0000-0ff1-ce00-000000000000` は SharePoint Online の第一者アプリケーション ID です ―
**この対応づけ自体は測定ではなく、広く知られた事実としての引用**です。

測定の側から言えることは 2 つあります。この `aud` を持つトークンは **ネットワーク往復を伴い、Graph の
トークンとは独立した有効期限を持ちます**。そして **実際に SharePoint REST に受け入れられます**
(所見 5)。どちらも「Graph のトークンを取り違えて返したもの」では説明がつきません。

じっと見る価値があるのは `scp` の値のほうです。`Sites.Read.All User.Read` は、**このアプリの
Microsoft Graph 委任付与の完全な写し** です ― 2 つとも、同じ順序で、それ以外は何もありません。

対比として、同じ実行の、同じ資格情報で:

| audience | モード | 結果 |
| --- | --- | --- |
| SharePoint | 委任 | トークン、`scp: Sites.Read.All User.Read` |
| Azure RMS | 委任 | 拒否、`AADSTS65001` |

違いは Graph 側の同意の有無と **対応しています** ― Azure RMS には対応する Graph の同意がなく、
SharePoint にはあります。**対応であって、因果を確かめたわけではありません。**

### これが意味すること

Microsoft Graph の委任 `Sites.Read.All` への同意が、SharePoint リソースに対する委任アクセスも生んで
います。**API アクセス許可の画面にそう書いてある箇所はありません。** その画面を読んで「このアプリは
利用者の代理で SharePoint に対して動けない」と結論するのは誤りであり、その画面をどれだけ読み込んでも
この事実は現れません。トークンを要求して中を見ることでしか表に出てきません。

### 確認していないこと

- **機構。** SharePoint リソース側での Graph の事前承認、第一者リソース間でのスコープ名の一致、
  管理者同意の副作用として作られたテナント全体の付与 ― いずれもこの結果を生みます。ここで実際に
  働いているのがどれかは特定していません。そして結果を報告するうえで、プローブがそれを知る必要は
  ありません。
- ~~そのトークンが実際に効くか。~~ **測りました。効きます** ― そして同じアプリの app-only は同じ
  エンドポイントで拒否されます。所見 5 を参照してください。
- **アプリケーション側の方向。** このアプリには SharePoint 自身の `Sites.Read.All` が明示的に付与されて
  いるため、この実行からは Graph の **アプリケーション** アクセス許可が同じように流れ込むかどうかは
  分かりません。それを知るには、SharePoint のアプリケーション付与を持たないアプリ登録が要ります。

### コードへの反映

当初この所見は `AuthProbe` の期待値表に「SharePoint / 委任は権限を保持する」と書き込む形で反映され
ました。**その期待値は後に、期待値という仕組みごと削除しました。** 3 つの所見のいずれもが、
アクセス許可の一覧から立てた予測を裏切っており、予測をコードに埋めて判定を出すことは、テナントに
ついてではなく作者の予測について報告することだったからです。いまツールが出すのは観測だけで、
期待はこの文書の「予測」節が担っています。

回帰を検知したい場合 ― 例えば Graph の委任付与を外したときにこのセルが変わることを捕まえたい場合 ―
は、2 つの実行の JSON レポートを差分で比べるのが素直です。

## 所見 2 ― クライアント資格情報は、何も持たないトークンを発行する

### 予測

Azure RMS のアクセス許可は両方向とも付与していないので、両方の経路が拒否されるはずである。

### 観測

2 つの経路が食い違う。

| モード | 結果 |
| --- | --- |
| 委任 | 拒否、`AADSTS65001` ― *"The user or administrator has not consented to use the application"* |
| app-only | **トークン発行**、`aud: https://aadrm.com`、`roles` なし、`scp` なし |

正しい audience 宛の、有効な、そしていかなる権限も持たないトークン。

### これが意味すること

`.default` は 2 つのフローで違うものを意味し、**ゼロ個のところで両者は袂を分かちます**。

| フロー | `.default` の意味 | 付与が 0 個のとき |
| --- | --- | --- |
| 委任 | このリソースに対してすでに同意済みのスコープ全部 | エラー ― `AADSTS65001` |
| クライアント資格情報 | このリソースに対して割り当て済みのアプリ ロール全部 | `roles` を持たないトークン |

つまりクライアント資格情報においては、トークン要求の成功が言っているのは **そのリソースのサービス
プリンシパルがテナントに存在すること** だけです。アプリがそれで何かしてよいかについては、何も言って
いません。

**そのサービス プリンシパルが存在することは、この測定自体が示しています。** 存在しなければ要求は
`AADSTS500011` (リソースが見つからない) で拒否され、`aud: https://aadrm.com` を持つトークンは返って
きません。**トークンが返ったこと自体が、相手が実在する証拠です。**

そのうえで、**このテナントの RMS はプロビジョニングされているだけではありません。** 保護つきの
秘密度ラベルが 3 つ構成・公開されており、使用権限は View / View+Print / View+DocEdit+Edit+Print+Export
の 3 段階です。マーキングも自動ラベル付けも無効なので、**このラベルは保護以外に何もしません**
([environment.md](environment.md) 参照)。

つまり空のトークンが出た相手は、**誰かが意図して組んだサービス**です。ただし「構成されている」と
「実際にラベルの付いたコンテンツがある」は別で、後者は測っていません。

(この段落は一度、「ラベルが 3 つ公開されている」だけを根拠に「RMS は実際に**使われている**」と
書いていました。**保護を適用しないラベルは RMS を使わない** ので、それは導けない推論でした。前提の
ほうを測ってから書き直しています。)

これこそ、このツール全体が踏まないために存在する罠です。「トークン発行 = 成功」と報告する能力プローブ
は、このアプリが Azure RMS に届いていると報告します。**`roles` が 1 つも無い以上、届いてはいないはず**
です ― ただしそれは推論で、下記のとおり **実際に呼んで確かめてはいません**。

### 追試 ― 空だったのは、割り当てが 0 個だったから

上の表の「クライアント資格情報の `.default` は割り当て済みのアプリ ロール全部」は、**仕様の引用で
あって測定ではありませんでした。** 引用が正しくても、このテナントでそれが理由だったとは限りません。

そこで **アプリ ロールを 1 つだけ足しました** ― Microsoft Rights Management Services の
`Content.DelegatedReader` (アプリケーション) に管理者同意。Graph と SharePoint の付与は触っていません。

| audience | 付与前 (14:04Z) | 付与後 (14:11Z) |
| --- | --- | --- |
| Graph | `roles: Sites.Read.All` | 変わらず |
| SharePoint | `roles: Sites.Read.All` | 変わらず |
| **Azure RMS** | **`no roles, no scp`** | **`roles: Content.DelegatedReader`** |

**動いたのは 1 セルだけ**で、しかもシークレットと証明書の両方が同じように動きました。同じスコープ、
同じアプリ、同じ資格情報、7 分差 ― **変えたのは付与 1 つです。**

> **トークンが空だったのは、割り当てが 0 個だったからです。** 1 つ割り当てると、同じ要求が
> それを載せて返ってきます。

これは **`.default` の一般則を証明するものではありません。** 測ったのは
**「このトークンの中身は、アプリ ロールの割り当てに追随する」** ことで、仕様の引用だった部分の
うち、このテナントで効いている因果だけが測定に変わりました。

**副産物が 1 つ。** シークレットと証明書が同じ内容を受け取ったことは、所見 5 の形とも整合します ―
**Entra が何を発行するかに名乗り方は効かず、効くのは受け取ったリソースの側**でした。

### 確認していないこと

- ~~このトークンで実際に Azure RMS の API を呼ぶと拒否されること。~~ **前提が変わりました。**
  いまは `Content.DelegatedReader` を持っているので、「空のトークンで呼ぶとどうなるか」は
  **もう測れません** ― 測るなら付与を外して戻す必要があります
- **`Content.DelegatedReader` を持ったトークンで実際に呼ぶと何が起きるか。** これがこの追試の
  目的で、まだ測っていません
- **付与を外すと空に戻るのかどうか。** 対称性は仮定していますが、測っていません

### コードへの反映

`auth` はトークンの発行だけを見るのをやめました。発行された各トークンから `roles` と `scp` のクレームを
読み、**何が付与されているか** を出力します。この変更により、このセルは初めから報告すべきだったことを
報告します: `token, but nothing granted`。

クレームは **読むだけで、検証はしません**。このツールはどのトークンの受け手でもなく、トークンに基づく
信頼の判断を一切しないので、署名の検証は誰も問うていない問いに答えることになります。そのための
トークン処理ライブラリも導入していません。

## 所見 3 ― 見せてもらえない権限一覧は、空の成功として返ってくる

### 予測

サインインする人物は閲覧者である。アイテムの権限一覧を読むことは閲覧者の領分ではないので、委任側は
`403` で拒否されるはずである。

### 観測

拒否されない。同じファイル、同じ瞬間、1 回の実行で:

| モード | site | item | permissions | 件数 | プリンシパルの種類 |
| --- | --- | --- | --- | --- | --- |
| app-only | `200 OK` | `200 OK` | `200 OK` | **4** | `sharePointGroup, siteGroup, siteUser, user` |
| 委任 | `200 OK` | `200 OK` | `200 OK` | **0** | ― |

6 つの呼び出しがすべて成功しています。Graph は委任の呼び出し元に、空のコレクションつきで `200 OK` と
答えます。

**測定はここまでです。** 「権限エントリは呼び出し元が見てよいものだけに絞られている」というのは、この
結果に最もよく合う読みですが、Graph の内部でそうなっているかを確かめたわけではありません。下の追試は
その読みを支持しますが、証明ではありません。

### これが意味すること

**ステータス コードでは、次の 2 つを区別できません。**

- このファイルは誰とも共有されていない
- このファイルの共有は自分に見せてもらえない

どちらも `200 OK` と `"value": []` です。委任側の答えだけを読んで「共有されていない」と結論するコード
は、真実の正反対を得ます ― ここでは権限エントリが 4 件あります。

これは `403` が返るより **たちが悪い** ものです。拒否は騒がしく、処理されない拒否はたいてい呼び出し元を
止めます。空の成功は静かで、次の処理にそのまま流れ込み、しかも情報のように見えます。

これは、このツールが `MeasurementStatus.NotRun` で内部的に防いでいるのと同じ危険でもあります ― *「そこまで到達
しなかったので見ていない」* を、合格のように読める空欄として保存してはならない ― ただしここでは、
Graph 自身の応答の形が 1 つ外側の層で同じ混同をやっています。

これが見えるようにしているものが 2 つあります。両方の経路が **1 回の実行** で走るので、2 つの答えは
同じアイテムの同じ瞬間を記述しており、突き合わせられます。別々の実行だったなら、この差は「その間に
何かが変わった」でいつでも説明がついてしまいます。もう 1 つは、**件数がステータスとは別に記録される**
ことです。そのおかげで `200 OK / 4` と `200 OK / 0` は互いに潰れ合いません。

### 追試 ― 絞り込みは「自分に関係するか」では決まらない

当初この所見は「閲覧者には見せてよい権限エントリが 1 件も無いから 0 件になる」と読めました。**その読みは
間違っていました。** 共有状態の違うファイルを 4 つ用意し、**1 回の実行で** すべてを両方の identity から
読んで確かめています。

| ファイル | 共有状態 | app-only | 委任 |
| --- | --- | --- | --- |
| A | 継承のみ | `200 OK` / **4 件** | `200 OK` / **0 件** |
| B | **委任ユーザー本人に直接アクセス許可を付与** | `200 OK` / **5 件** | `200 OK` / **0 件** |
| C | 組織内リンクで共有 (`link:organization`) | `200 OK` / **5 件** | `200 OK` / **0 件** |
| D | 継承を切ったフォルダ内 (閲覧者を削除) | `200 OK` / **3 件** | アイテムが `404` (所見 4) |

**B が決定的です。** このファイルには「このユーザーに閲覧を許可する」という、**サインインしている本人を
名指しした権限エントリ** があります (app-only の件数が 4 から 5 に増えていることがその証拠です)。それでも
本人には見えません。

つまり絞り込みは *「あなたに関係するエントリを見せる」* ではありません。**権限一覧を読むこと自体が
できるかどうか** で決まっており、閲覧者にはできない。自分宛の許可であっても、自分では確認できません。

C も同じで、`link:organization` のエントリは app-only にしか現れません。

app-only 側の件数は互いに整合しています。A の 4 件が基準で、B と C は付与を 1 つ足した分だけ増え、
D は閲覧者グループを外した分だけ減っています。**ツールが数えている件数が、実際に権限を触った操作を
反映している** ことの確認になります。

この追試は所見を弱めるのではなく、はっきりさせています。委任側の 0 件は「たまたま見せるものが
無かった」ではなく、**そのファイルの共有状態がどうであれ 0 件** です。したがって「0 件だったから
共有されていない」という読みは、いかなる場合にも成り立ちません。

### 確認していないこと

サイトに対してより強い権限を持つ委任呼び出し元 ― 閲覧者ではなくメンバーや所有者 ― が空でない一覧を
見るかどうか。それが確認できれば、絞り込みが呼び出し元の権限によるものだと裏付けられます。別の
アカウントで `access` を走らせるだけで済みます。

### コードへの反映

レポートは **ステータスと件数を別々に記録します**。この 2 つが独立でなければ、`200 OK / 4 件` と
`200 OK / 0 件` は互いに潰れ合います。また、成功した応答が 0 件だった場合は観測の文言に
「拒否ではなく空の一覧」と書き添え、2 つの経路が同じステータスで違う中身を返した場合もその旨を
書きます ― 読み手が数字から自力で気づくのに任せません。

なお、この所見も当初は「委任側は権限エントリを明かさない」という主張と判定の形で書かれていました。
いまは判定を出しません。**「明かさないはずだ」は予測であり、それはこの文書が担うべきものだから**です。

## 所見 4 ― 見えないファイルと、存在しないファイルは、同じ答えを返す

### 予測

継承を切って閲覧者グループを外したフォルダの中のファイルは、委任側から読めないはずである。`403` で
拒否されるか、`404` で無いことにされるかは分からないが、**`404` だろう** ― Graph は見る権限のない
アイテムを not found として扱うと聞く。

### 観測

`404 Not Found`、Graph のエラーコードは **`itemNotFound`**。

| モード | site | item | permissions |
| --- | --- | --- | --- |
| app-only | `200 OK` | `200 OK` | `200 OK` / 3 件 |
| 委任 | `200 OK` | **`404 Not Found` `itemNotFound`** | (到達せず) |

app-only 側の件数は 3 件で、他のファイルは 4 件です。**継承を切って閲覧者グループを外した分だけ
減っている** と読めます ― ただし **どのエントリが消えたかは記録していない** ので、対応づけは推測です。

### これが意味すること

`404 itemNotFound` は、**パスを書き間違えたときに返るのと同じ答え**です。区別する手がかりは応答の中に
ありません。

これは机上の心配ではありません。この文書を書いた作業では、読むファイルのパスの書き方を間違えて
(`/Shared Documents/test.docx` とライブラリ名を付けてしまい) **まったく同じ `404 itemNotFound` を実際に
踏んでいます**。そのときは設定の誤りでしたが、応答は今回と一文字も違いません。

つまり委任側で `404` を受け取ったコードは、次の 3 つを区別できません。

- パスが間違っている
- ファイルが存在しない (消された)
- ファイルは存在するが、この呼び出し元には見えない

3 番目だけが権限の話で、他の 2 つは違います。**「404 だったので存在しない」と結論するのは、
「0 件だったので共有されていない」(所見 3) と同じ形の間違い** です。

これを解けるのは、**同じパスを別の identity で同時に引くこと** だけです。app-only が `200` を返して
委任が `404` を返したなら、そのファイルは存在していて、見せてもらえないだけだと分かります。これは
1 回の実行で両方を叩く設計でなければ得られません ― 別々の実行なら「その間に消えた」で説明がつきます。

### 確認していないこと

- サイト自体が見えない場合に何が返るか。ここではサイトの解決は委任側でも `200` で通っています
- `403` が返る条件があるのかどうか。このテナントのこの構成では観測できていません

### コードへの反映

**終了コードの意味を直しました。** アイテムが `404` だったため権限一覧の呼び出しが行われず、その行が
`NotRun` になります。それまで `NotRun` が 1 つでもあれば終了コードは `2` (不完全) でしたが、**これは
誤りでした。** この実行は完全です ― 404 が答えであり、答えられない問いを組み立てなかったのは正しい
振る舞いです。

`NotRun` は「上流の測定結果がその先を到達不能にした」ことを意味し、その上流の測定こそが所見です。
不完全なのは 1 つの場合だけ ― **デバイス コードを出したのに誰もサインインしなかった** ときで、これは
測定ではなく操作の失敗です。終了コード `2` はそこに限定しました。

完全に有効な測定を CI が赤で表示すると、読み手は赤を無視するようになります。

## 所見 5 ― 付与されていない側が通り、付与されている側が拒否される

### 予測

立てませんでした。所見 1 で「Graph の同意が SharePoint に流れ込んで `scp` に載る」ところまでは見えて
いましたが、**そういう経路で届いたクレームを SharePoint が受け入れるかどうかは分からない**、というのが
正直なところだったので、旗を立てずに測りました。

app-only については、SharePoint 自身の `Sites.Read.All` を明示的に付与し管理者同意も与えてあるので、
通ると考えていました。

### 観測

**両方とも外れています。しかも向きが逆です。**

| | 付与されているもの | トークンが持つもの | `GET /_api/web` |
| --- | --- | --- | --- |
| app-only | SharePoint `Sites.Read.All` (アプリケーション、**同意済み**) | `roles: Sites.Read.All` | **`401 Unauthorized`** |
| 委任 | **何も無い** | `scp: Sites.Read.All User.Read` | **`200 OK`** (`Title` が返る) |

`/_api/web/currentuser` も同じ結果で、委任側は SharePoint が認識している呼び出し元として
**サインインした本人**を返します (`i:0#.f|membership|…`)。app-only 側は同じく `401`。

**アクセス許可の画面が言っていることの、正確に反対です。**

### これが意味すること

**`403` ではなく `401` である**ことが重要です。`403` なら「認証はされたが、この操作をする権限がない」
という意味になります。`401` は **そもそも資格情報として受け付けられていない**。SharePoint はこの
呼び出し元を「権限の足りない誰か」とすら見なしていません。

返ってくる `WWW-Authenticate` が **素の challenge** であることが、それを裏づけます。

```
no reason given (realm, client_id, trusted_issuers, authorization_uri)
```

**理由を述べるパラメータが 1 つもありません。** `error=` も `error_description=` も付かず、本文は空、
`x-ms-diagnostics` も返りません。あるのは realm と、リソース自身の ID と、信頼する発行者と、認証しに
行く先だけ ― **「認証してください」** と言っているだけです。

トークンを添えて呼んだのに、**認証していない相手として扱われています。** SharePoint から見て、この
呼び出しには資格情報が付いていなかったのと同じです。

(上の 1 行はレポートの実際の出力です。値ではなくパラメータ名を並べているのは、素の challenge が
realm にテナントを名乗るためで、CI のログでは値が伏せ字になります。名前は誰の秘密でもないので
そこを通り抜けます。)

そして決定的なのは、**同じ app-only トークンが Graph 経由では通っている**ことです。所見 3 の測定で、
app-only は Graph の `/permissions` から権限エントリを 4 件読めています。つまり:

> **このアプリが SharePoint に届かないのではありません。どの API を通るかで、通れるかどうかが
> 変わります。**

これは所見 1 から続く階層をもう 1 段深くします。**アクセス許可の画面**、**トークンのクレーム**、
**リソースの応答** の 3 つが食い違うことは所見 1〜4 で見てきましたが、ここではさらに
**同じ権限・同じトークンでも、経路によって答えが変わる**。`auth` の出力だけを見て
「app-only は SharePoint に `Sites.Read.All` を持っている」と読み、SharePoint REST を叩く実装を
書くと、`401` に出迎えられます。

### 追試 ― 経路の問題であることの担保と、拒否の一様さ

呼び出しを増やし、**同じ実行で Graph にも 1 本投げて対照**にしました。

| 呼び出し | app-only | 委任 |
| --- | --- | --- |
| **Graph** `GET /v1.0/sites/{host}:{path}` | **`200 OK`** | **`200 OK`** |
| `GET /_api/web` | `401` | `200 OK` |
| `GET /_api/web/currentuser` | `401` | `200 OK` |
| `GET /_api/web/sitegroups` | `401` | `200 OK` |
| `GET /_api/web/sitegroups({id})/users` | `401` | `403` (所見 6) |

**対照が効いています。** Graph は同じ実行・同じ資格情報・同じサイトに対して app-only でも `200` を
返します。したがって `/_api/` の `401` は、**アプリが壊れているのでも、資格情報が無効なのでも、
テナントに届かないのでもありません。経路が違うだけ**です。この 1 行が無ければ、拒否が並んだ画面は
何とでも読めてしまいました。

**そして app-only の拒否は一様です。** 4 つのエンドポイントすべてで `401`、いずれも同じ素の
challenge。特定の操作が禁じられているのではなく、**この経路でこの identity が受け付けられていない**。

### 追試 2 ― 権限の強さは変数ではない (**この見出しは狭めました。追試 4 参照**)

アプリの SharePoint アクセス許可を **`Sites.Read.All` から `Sites.FullControl.All` (アプリケーション)
に差し替えて管理者同意**し、同じ測定を繰り返しました。Microsoft Graph 側の付与は触っていません。

| | 1 回目 | 2 回目 |
| --- | --- | --- |
| トークンの `roles` | `Sites.Read.All` | **`Sites.FullControl.All`** |
| app-only `GET /_api/web` | `401` | **`401`** |
| app-only `GET /_api/web/currentuser` | `401` | **`401`** |
| app-only `GET /_api/web/sitegroups` | `401` | **`401`** |
| app-only `GET /_api/web/sitegroups({id})/users` | `401` | **`401`** |
| *(対照)* Graph app-only | `200` | `200` |
| *(対照)* 委任 4 本 | `200 200 200 403` | `200 200 200 403` |

**何も変わりません。**

対照が 2 つとも動いていないので、2 つの実行の間で変わったのは **SharePoint のアプリ ロールだけ** です。
したがって:

> **このトークンについては、権限の強さは変数ではありません。** テナント内の全サイト コレクションに
> 対するフル コントロールを持っていても、`/_api/` は同じ `401` を返します。

これは `403` ではなく `401` だという観測と辻褄が合います。**SharePoint はこのトークンについて
ロールを見てすらいません** ― 見ていれば、`Sites.Read.All` と `Sites.FullControl.All` で何かが違った
はずです。「権限が足りない」という説明は、**シークレットで名乗った app-only については**消えました。

**これは否定的な結果で、否定的な結果は見えにくいものです。** `Sites.FullControl.All` だけで 1 回
測っていたら、「app-only は SharePoint REST を叩けない」で終わり、**権限を足せば通るのかどうかは
分からないまま**でした。「何も変わらなかった」が所見になるのは、**同じ測定が 2 つの付与状態で
比較できる形で残っている**からです。レポートのヘッダが `roles` を持っているのは、そのためです。

> **【後日の訂正】** ここでもとは「権限の強さは変数ではありません」と、トークンの種類を限定せずに
> 書いていました。**追試 4 で、それは広すぎたことが分かりました。** 証明書で名乗った app-only では、
> `Sites.Read.All` と `Sites.FullControl.All` で答えが変わります。この追試が測ったのは
> **「`appidacr: 1` のトークンについては権限が変数ではない」** ことで、当時はそれ以外のトークンを
> 持っていなかったので、区別がつきませんでした。上の本文は、その限定を入れて書き直してあります。

### 追試 3 ― 変数は「名乗り方」だった

追試 2 が消したのは **「権限の量が足りない」** という説明だけでした。残っていた候補のうち 1 つは、
`/_api/` が受け付けるかどうかが **アプリの持つロールではなく、アプリが Entra に対してどう名乗ったか**
に依るというもので、これは権限の強弱とは別の次元です。**予測は立てずに測りました。**

アプリ登録に自己署名証明書を 1 つ登録し、ツールに **3 本目のレグ** を足しました ―
**同じアプリ登録・同じ付与のまま、シークレットの代わりに証明書で名乗る app-only** です。3 本すべてを
同じ実行の中で要求します (2026-08-04、GitHub ホストのランナー)。

| 呼び出し | app-only (シークレット) | app-only (**証明書**) | 委任 |
| --- | --- | --- | --- |
| *(対照)* Graph `/sites/{host}:{path}` | `200` | `200` | `200` |
| `GET /_api/web` | `401` | **`200 OK`** | `200` |
| `GET /_api/web/currentuser` | `401` | **`200 OK`** | `200` |
| `GET /_api/web/sitegroups` | `401` | **`200 OK`** ― 6 グループ | `200` ― 6 グループ |
| `GET /_api/web/sitegroups({id})/users` | `401` | **`403 Forbidden`** | `403 Forbidden` |

**2 つの app-only トークンは、レポート上で見分けがつきません。**

| | 付与 | トークンの `roles` | `aud` |
| --- | --- | --- | --- |
| シークレット | SharePoint `Sites.Read.All` | `Sites.Read.All` | `00000003-0000-0ff1-ce00-000000000000` |
| 証明書 | **同じ** (同じアプリ登録) | **`Sites.Read.All`** | **同じ** |

同じテナント、同じクライアント ID、同じアプリ ロール、同じ audience、同じランナー、数百ミリ秒差。
**違うのは Entra に対する名乗り方だけです。** したがって:

> **`/_api/` が app-only トークンを受け付けるかどうかを決めているのは、権限ではなく、アプリが
> どう認証したかです。** シークレットで取ったトークンは `401`、証明書で取ったトークンは `200`。
> 同じロールを持った、同じアプリの、同じ瞬間のトークンで。

**所見 5 の「経路によって変わる」という読みは、狭すぎました。** 経路 (Graph か `/_api/` か) も効いて
いますが、`/_api/` の中でさらに **資格情報の種類** が効いています。Graph は両方受け付け、`/_api/` は
片方だけを受け付けます。

### 追試 3b ― 差はトークンの中に見える

追試 3 のあと、トークンの `appidacr` クレームを記録するようにして、**同じ測定をもう一度**
回しました (2026-08-04、12 分後、同じランナー種別)。**5 本の呼び出しの結果は 1 つも変わらず**、
新しく読めるようになったのがこれです。

| レグ | 使った資格情報 (こちらが知っていること) | トークンの `appidacr` | `/_api/web` |
| --- | --- | --- | --- |
| app-only (シークレット) | クライアント シークレット | **`1`** | `401` |
| app-only (証明書) | 秘密鍵による署名 | **`2`** | `200` |
| 委任 | デバイス コード (パブリック クライアント) | **`0`** | `200` |

**3 本が 3 つとも違う値を持っていました。** そしてこの対応は、**このプローブ自身の実行の中で確かめた
もの**です ― どのレグがどの資格情報を使ったかはこちらが決めており、その 3 本に 3 つの異なる値が
返りました。値の一般的な意味は依然として**引いていません**が、**この 3 本については、クレームが
名乗り方に対応して動いた**ことが測れています。

これで言い方が 1 段正確になります。

> **`/_api/` が拒んでいるのは、`appidacr: 1` のトークンです。** `2` も `0` も通っています。
> 「証明書だけを受け付ける」ではなく、**シークレットで取ったものだけを拒む**、というのが
> 観測に合う形です。

**ただし委任の `0` は 1 変数の比較ではありません。** 委任トークンは `roles` ではなく `scp` を持ち、
背後に利用者がいます ― シークレットとの違いは `appidacr` だけではないので、この行は
「拒まれるのは `1` だけ」を **補強はしても、単独では証明しません**。1 変数で比べられているのは、
依然としてシークレットと証明書の 2 本だけです。

**証明書レグはアプリとして認識されています。** `currentuser` が返したのは:

```
i:0i.t|00000003-0000-0ff1-ce00-000000000000|app@sharepoint
```

利用者ではなく **アプリの identity** です。委任側の `i:0#.f|membership|<upn>` とは別物で、
**2 つのレグはトークン エンドポイントの上だけでなく、リソースの上でも別の identity** でした。
シークレット側は `401` なので、SharePoint がそれを誰だと思っていたかは分かりません ― **誰とも
思っていない**、というのが `401` の意味です。

### 追試 3 の限界

- **2 回の観測です。** シークレットの `401` は 5 回、委任の `200` は 5 回再現していますが、
  **証明書の `200` は 2 回** ― 12 分差の連続した 2 回で、どちらも同じジョブ形態です。日をまたいだ
  再現は取れていません
- **機構は分かりません。** 「なぜ SharePoint が `appidacr: 1` のトークンを拒むのか」は測って
  いません。この観測は **どの変数が効いているか** を示しただけで、**なぜ効くのか** は示していません
- **テナント設定か仕様かを切り分けていません。** テナント側にそういう設定があってそれが効いている
  のか、`/_api/` の恒常的な振る舞いなのかは分かりません。**片方だけを測っても区別できない**種類の
  問いで、区別するには設定を動かすか、別のテナントで測るかが要ります
- **拒否の理由は依然として返ってきません。** シークレット側の `WWW-Authenticate` は追試 1 と同じ素の
  challenge で、証明書に切り替えると通る、という手がかりは **応答の中には 1 文字もありません**
- **このテナントの話です。** 他のテナントや他の構成で同じかどうかは確かめていません

### コードへの反映 (追試 3)

トークンの **`appidacr` / `azpacr` クレーム** を読んで記録するようにしました。これは
「アプリがどう認証したか」を発行側が書き込む唯一の欄で、**追試 3 で効いた変数がトークンの中に見える
形で現れる唯一の場所** です。これが無いと、同じに見える 2 つのトークンが違う扱いを受けたという所見に、
レポートの中で引っかかるところがありません ― **追試 3b は、この列を足したから取れた測定** です。

**値は生のまま出します。** Entra は数値の意味を公開していますが、**このプローブはその対応を測って
いません**。トークンが `2` と言っているところに「証明書」と書けば、調べ物を観測として出すことに
なります ― グループの `PrincipalType` を生の数値のままにしているのと同じ規則です。

**追試 3b で分かったのは、あくまで「この 3 本については、値が名乗り方に対応して動いた」ことだけ**
です。`1` が一般に何を意味するかは、この文書のどこにも書いていません。

### 追試 4 ― 権限は変数だった。ただし門を通ったあとだけ

追試 2 (フル コントロール) と追試 3 (証明書) を **交差させました**。アプリの SharePoint アクセス許可を
もう一度 `Sites.FullControl.All` (アプリケーション) に差し替え、証明書レグを持ったまま同じ測定を
回します (2026-08-04、追試 3b の 23 分後、同じランナー種別)。Graph 側も証明書も触っていません。

| 呼び出し | シークレット (`appidacr: 1`) | 証明書 (`appidacr: 2`) | 委任 (`appidacr: 0`) |
| --- | --- | --- | --- |
| *(対照)* Graph `/sites/{host}:{path}` | `200` | `200` | `200` |
| `GET /_api/web` | `401` | `200` | `200` |
| `GET /_api/web/currentuser` | `401` | `200` | `200` |
| `GET /_api/web/sitegroups` | `401` | `200` | `200` |
| `GET /_api/web/sitegroups({id})/users` | `401` | **`200 OK` ― 0 メンバー** | `403` |

**1 セルだけ動きました。** 証明書レグのグループ メンバー列挙が、`403` から `200` に変わっています。
他の 14 本は追試 3b と 1 本も違いません。委任側は `403` のままで、アプリ ロールを使わないレグが
動かなかったことが、変えたのがアプリ側だけであることの担保になっています。

したがって、**変数は 2 つあり、順番があります。**

| | 変数 | 通らなかったとき | 証拠 |
| --- | --- | --- | --- |
| 1 段目 | **資格情報の種類** | `401` ― **権限は参照されない** | 追試 2: フル コントロールでも `401` |
| 2 段目 | **権限の強さ** | `403` | 追試 4: `Read.All` で `403`、`FullControl.All` で `200` |

> **`/_api/` は 2 段構えです。** まず「この資格情報は受け付けるか」を見て、通らなければ権限を
> 見ずに `401` を返します。通った先で初めて権限が効き、足りなければ `403` になります。
> **追試 2 が「権限は変数ではない」に見えたのは、当時のトークンが 1 段目で止まっていたからです。**

これは追試 2 の結論を **否定するのではなく、限定します**。あの実行が測っていたのは
`appidacr: 1` のトークンで、**そのトークンについては今も権限は変数ではありません** (追試 4 の
シークレット列は 4 本とも `401` のまま)。広すぎたのは、そこから「`/_api/` は権限を見ない」と
一般化した部分です。

**そして所見 6 の「何なら足りるのか」も埋まりました。** グループのメンバー列挙には
`Sites.Read.All` (アプリケーション) では足りず、`Sites.FullControl.All` で足ります ―
**証明書で名乗った app-only については**。

### 追試 4 の限界 ― `0 メンバー` が何についての事実か

**通った先にあったのは、空のグループでした。** これは 2 つのことを言っています。

- **委任側の `403` の向こうにあったのは、0 件だった。** 同じ実行、同じ瞬間、同じグループを、
  証明書レグは `200 OK` / 0 メンバーで読み、委任レグは `403` で断られています。所見 3 の
  「絞られた `200`」と裏返しで、**ここでは拒否のほうが、空であることを隠していました**
- **ただし、そのグループは選んだものではありません。** 実装は一覧の **先頭のグループ** を使い、
  この実行で先頭に来ていたのは `Limited Access System Group For List <GUID>` ― 所見 6 の副産物で
  触れた、**SharePoint が自分の都合で作ったとみられるグループ**です。`閲覧者` グループではありません

つまり **`0 メンバー` は、システム生成とみられるグループについての事実**であり、
**人が入っているグループでも同じ結果になるかは測っていません**。「メンバーを列挙できた」ことは
測れましたが、「メンバーを **見た**」とまでは言えません ― 見るべき中身がありませんでした。

**この危うさは、レポートの側で塞ぎました。** 対象グループの **名前を ID と並べて記録**します。
どのグループを読んだかで `0 メンバー` の意味は変わるのに、番号だけでは読み手に区別のしようが
ありません。

その他の限界:

- **1 回の観測です。** 追試 2 のときと同じで、付与状態を戻したあとにもう一度は測っていません
- **`FullControl` と `Read` の間は測っていません。** 足りる境界がどこかは分かりません
- **権限を戻すと `403` に戻るのか** も確かめていません (対称性は仮定していますが、測っていません)

### 確認していないこと

  いません。詳しくは上記。
- ~~機構。~~ **効いている変数は 2 つとも特定しました** (追試 3: 資格情報の種類 / 追試 4: 権限の強さ。

- ~~Graph 側との対比の範囲。~~ **追試で埋めました** ― 同じ実行で Graph にも 1 本投げ、app-only でも

### 読むときの注意 ― CI のログはレポートそのものではない

この所見を取った実行で、`WWW-Authenticate` の中身は **GitHub Actions によって伏せられていました**。
ヘッダが `realm="<テナント ID>"` を含み、そのテナント ID がワークフローのシークレットとして登録されて
いるためです。**正しい動作ですが、測定値の一部が読めなくなります。**

しかも伏せ字への置換は**ログに書かれた後**に起きるので、表の桁が崩れます ― それが起きていること自体の
手がかりになります。

CI のログから読むかぎり、**レポートには写っていても読み手には届かない部分がありえます。** 識別子を
含みうる値を追うときは、シークレットの登録がないローカルで走らせるほうが確実です。

### コードへの反映

**応答ヘッダを記録するようにしました。** 本文が空の拒否について「拒否された、理由は不明」と記録して
いたのは、**理由を言っているサービスに対してこちらが聞いていなかった** ということです。「失敗は
測定値」と言いながら、測定値の半分を捨てていました。

`WWW-Authenticate` / `x-ms-diagnostics` / 相関 ID などを許可リストで拾い、本文にエラーコードが無い
場合はコンソールの「なぜ拒否されたか」欄に出します。全部ではなく許可リストなのは、応答ヘッダの大半が
運搬の事務であって、記録は読めることに意味があるからです。

**ヘッダは丸ごと出すのではなく、意味のある名前つきパラメータだけを抜き出します。** `WWW-Authenticate`
の challenge は、realm・リソース・信頼する発行者を名乗るのに最初の百数十文字を使い、`error=` があれば
その後ろに来ます。丸ごと出すと **理由の部分が切り詰めで落ちる** ので、`error` / `error_description` /
`reason` / `error_category` だけを残します。

**そして理由が 1 つも無かったときは、そう書きます。** 「ヘッダはあるが理由を含まない」と「ヘッダが
無い」と「読めなかった」は 3 つとも別の観測なので、3 つとも別の文言になります。理由が無い場合は
**値ではなくパラメータ名を並べます** ― 素の challenge は realm にテナントを名乗るので、CI のログでは
値が伏せ字になり、答えの形まで一緒に消えます。名前は誰の秘密でもないので、そこを通り抜けます。

この一連の直しの出発点は、レポートが **「拒否された、理由は不明」と「拒否された、理由は述べられて
いない」を同じ見た目で出していた** ことでした。前者はこちらの落ち度で、後者は観測です。

**この所見は、確定するまでにツールを 3 回直しています。** 1 回目は応答ヘッダを
まったく記録していませんでした。2 回目は記録したものの、定型が長すぎて意味のある部分が桁の切り詰めで
落ちました。3 回目でようやく「理由が無い」と「読めない」を分けました。**測定器が測れないものは、
測定対象の性質のように見えます。** 所見 3 と 4 で Graph について言ったのと同じことが、こちら側でも
起きていたわけです。

## 所見 6 ― 一覧はできるが、中身は見せない ― そして今度は `403`

> **【後日の訂正】この見出しは、サイトのグループ全体については成り立ちません。**
> この所見と最初の追試は **1 つのグループ** についての測定で、しかもそのグループは誰も選んで
> いません (実装が一覧の先頭を取っていた)。6 つ全部に訊いたところ、**中身が見せてもらえない
> のは 6 つ中 3 つだけ**で、しかもその 3 つは **SharePoint が自分の都合で作ったグループ**でした。
> `probe メンバー` `probe 閲覧者` `probe 所有者` の 3 つは、`Sites.Read.All` のままでも、
> 委任でも証明書レグでも **`200` で中身が返ります**。詳細は下の追試 2。
> 以下の観測そのものは正しく、**一般化した部分だけ**が間違っていました。

### 予測

書きませんでした。app-only が `/_api/` に通る条件を探す実行だったので、委任側は付き添いのつもりでした。

### 観測

**委任側でグループは一覧できます。中身は拒否されます。**

| 呼び出し | 委任 |
| --- | --- |
| `GET /_api/web/sitegroups` | **`200 OK`** ― 6 グループ、名前つき |
| `GET /_api/web/sitegroups({id})/users` | **`403 Forbidden`** |

`403` です。**`401` ではありません。**

### これが意味すること

**同じ実行のなかに、断られ方が 3 つ揃いました。**

| 断られ方 | どこで | 何が起きているか |
| --- | --- | --- |
| `401` + 素の challenge | app-only (シークレット)、`/_api/` の全部 | **認証されていない。** 資格情報として受け付けられていない |
| `403` | 委任、グループの中身 | **認証されている。操作が拒否された** |
| `200` + 空/絞り込み | 委任、Graph の権限一覧 (所見 3) | **認証も認可も通った。中身が絞られた** |

所見 5 で「`403` ではなく `401` である」ことを重要だと書きましたが、それは対比する `403` を持たない
主張でした。**いまは同じ実行の、同じ API から出た `403` が隣にあります。** SharePoint はこの 2 つを
実際に使い分けており、app-only に返しているのは「あなたが誰かは分かったが権限が足りない」ではなく
**「あなたが誰か分からない」** のほうだと確定します。

### 追試 1 ― `403` は委任だけのものではない (**対象は 1 グループ。追試 3 参照**)

所見 5 の追試 3 で証明書レグを足したところ、**アプリの identity も同じ形で断られました。**

| 呼び出し | app-only (証明書) | 委任 |
| --- | --- | --- |
| `GET /_api/web/sitegroups` | `200 OK` ― 6 グループ | `200 OK` ― 6 グループ |
| `GET /_api/web/sitegroups({id})/users` | **`403 Forbidden`** | `403 Forbidden` |

証明書レグは `Sites.Read.All` を **アプリケーション** ロールとして持ち、サイトを読め、グループを
一覧でき、**それでもメンバーは見せてもらえません**。この行を書いた時点で持っていた読み ―
「閲覧者はグループの中身を見られない」 ― は、**利用者の役割の話としては狭すぎました。**

> **「一覧はできるが中身は見せない」は、閲覧者という役割の性質ではありません。** 少なくとも
> このサイトの、この 1 つのグループについては、**アプリの identity にも同じ答えが返ります。**

ただし **これも 1 回、1 グループの観測** です。「サイトのメンバー全員に一律」なのか「たまたまこの
グループがそう」なのかは、**分けられていません**。

そしてもう 1 つ、否定的な形で分かったこと: **ここでは `Sites.Read.All` というアプリケーション
ロールでは足りていません** ― 足りているなら、サイトが読めた identity が同じ呼び出しで断られる理由が
ありません。

### 追試 2 ― 足りるものが分かった (**対象は 1 グループ。追試 3 参照**)

所見 5 の追試 4 で `Sites.FullControl.All` に差し替えたところ、**証明書レグのこの `403` が `200` に
変わりました。** 動いたのは 15 本中この 1 本だけです。

| 付与 | 証明書レグの `sitegroups({id})/users` | 委任 |
| --- | --- | --- |
| `Sites.Read.All` | `403 Forbidden` | `403 Forbidden` |
| **`Sites.FullControl.All`** | **`200 OK` ― 0 メンバー** | `403 Forbidden` (変わらず) |

**「一覧はできるが中身は見せない」は、アプリの identity については権限で動きます。** 委任側は
アプリ ロールを使わないので変わらず、そこは役割の話のままです。

**そして `200` の中身は 0 件でした。** 委任側の `403` が隠していたのは、**空のグループ**です ―
同じ実行、同じ瞬間、同じグループで。ただし対象は一覧の先頭に来た
`Limited Access System Group For List <GUID>` で、**上で「自動生成とみられる」と書いたそれ**です。
`閲覧者` グループではありません。詳しくは所見 5 の「追試 4 の限界」を参照してください。

そしてもう 1 つ。**「グループの一覧」と「グループの中身」は、少なくとも一部のグループについて別の
権限です。** 一覧は 6 つとも返るのに、中身が返るのは 3 つだけ ― **一覧のほうが広い**、という形は
残ります (**ただし「中身は一切見せない」ではありません**。追試 3)。

所見 3 で Graph 側について見たのと同じ形 ― *誰がアクセスを持っているか* は、アクセスを持っている
だけの人には見せない ― が、SharePoint REST でも部分的に成り立っています。**ただし現れ方が違います。**
Graph は `200` と空のコレクションで、SharePoint は `403` で。

**2 つが同じ方針から出ているのかは分かりません** ― 対象も違えば (ファイルの権限エントリと、グループの
メンバー) API も違います。言えるのは、**似た問いに対して 2 つの API が違う断り方をする** ことです。

## 所見 8 ― ACL は束で取れる。ただし経路は 1 つだけ

### 予測

立てていません。**候補を 3 つ並べて、どれが通るかを測りました。**

### 観測

所見 3 と 4 は、権限一覧を **アイテム 1 件につき 1 回** 読んで得たものです。ファイルの数だけ呼ぶと
いうことは、ライブラリ全体の ACL を毎回読むのは、ファイルが数個のうちしか成り立ちません。安い経路が
あるかどうかを、`Sites.Read.All` と `Sites.FullControl.All` の 2 つの付与で測りました
(2026-08-04、GitHub ホストのランナー、app-only の 2 本のみ)。

| 経路 | 歩く範囲 | `Read.All` | `FullControl.All` |
| --- | --- | --- | --- |
| **基準** ― `children` + 件数だけ `/permissions` | ルート直下 | **5 回 / 4 件 / 17 エントリ** | 同じ |
| A ― Graph `children?$expand=permissions` | ルート直下 | **`400 notSupported`** | **`400 notSupported`** |
| B ― Graph `delta?$expand=permissions` | ドライブ全体 | **`501 notSupported`** | **`501 notSupported`** |
| C ― SP `items?$expand=RoleAssignments` (証明書) | リスト全体 | **`403`** | **`200` ― 2 回 / 5 件 / 18 エントリ** |
| C ― 同上 (シークレット) | リスト全体 | `401` | **`401`** |

> **束で取れます。ただし経路は 1 つだけで、条件が 3 つ揃ったときだけです** ―
> **SharePoint REST** であること、**証明書で名乗った** app-only であること、
> **`Sites.FullControl.All`** を持っていること。

### コストの形が変わります

これが問いの本体でした。**回数の「量」ではなく「形」が違います。**

| | 呼び出し回数 | 4 件のとき | 100 件のとき (外挿) |
| --- | --- | --- | --- |
| 基準 | **1 + 件数** | 5 回 / 2893 ms | 101 回 |
| C | **2 回** (探索 1 + 本体 1) | **2 回 / 662 ms** | **2 回** |

**基準は件数に比例し、C は比例しません。** 4 件で 5 回対 2 回というのは大した差に見えませんが、
**差が開き続ける**ことのほうが所見です。「毎回、全ファイルの ACL を読む」は、この経路でなら
現実的になります。

**ただし外挿は外挿です。** 測ったのは 1 ページ (`$top=100`、続きのページなし) だけで、
**ページをまたいだときに 1 ページ 1 回で済むかは測っていません。**

### A と B は権限の話ですらありません

`notSupported` は 2 つの付与状態でも、2 つの identity でも同じでした。**権限を動かしても
動きません** ― 所見 5 の追試 2 と同じ形の否定的な結果です。返しているのは Graph 自身のコードで、
「そういう組み合わせは提供していない」と言っています。

**ただし、それぞれ 1 通りの書き方しか試していません。** `$select` と併用するなど別の形なら通る
可能性は潰していません。測ったのは **「この書き方では受け付けられない」** までです。

### C は所見 5・6 の並びをもう一度なぞります

証明書レグは `Read.All` で **`403`**、`FullControl.All` で **`200`**。シークレットレグは
どちらでも **`401`**。**所見 5 の 2 段構え**（1 段目は資格情報、2 段目は権限）と、**所見 6 の追試**
（`Read.All` では足りず `FullControl.All` で足りる）を、**別の呼び出しでもう一度なぞっています。**

3 つ目の独立した例なので、あの形はこのテナントでは相当に安定していると言えます。
**なぜそうなのかは、相変わらず測っていません。**

### 件数が違うのは、食い違いではありません

C は **5 件**、基準は **4 件** を返します。**同じことを訊いていないからです。**

- 基準と A は `/drive/root/children` ― **ルート直下だけ**（3 ファイル + `restricted` フォルダ）
- C は リストのアイテム ― **入れ子も含めた全体**（そこに `restricted` の中のファイル D が加わる）

つまり C は **再帰しなくてよい**という利点も持っています。基準で同じ範囲を取るなら、フォルダごとに
`children` を辿る呼び出しがさらに要ります。

**17 と 18 というエントリ数を並べて「ほぼ一致」と読んではいけません。** 対象の集合が違ううえ、
**SharePoint の RoleAssignment と Graph の権限エントリは別のオブジェクト**です。ツールはこの 2 つを
突き合わせません ― 突き合わせれば「2 つのモデルは対応する」と主張することになり、それは測って
いません。

### コードへの反映

**経路ごとに「何を歩くか」を出すようにしました。** 5 件と 4 件が並んでいるのに、**なぜ違うのかが
レポートから読めませんでした** ― 番号だけでは食い違いに見えます。あわせて **アイテム 1 件ごとの
内訳** (名前と ACL の形) を JSON に出すので、件数を信じる代わりに確かめられます。

所見 6 で「グループの名前を ID と並べて記録する」ようにしたのと同じ理由です。**数だけでは、
何についての数かが分かりません。**

### 確認していないこと

- **ページをまたいだときの挙動。** 1 ページ (`$top=100`) しか測っていません
- **`Read.All` と `FullControl.All` の間のどこが境界か**
- **委任ではどうか。** この 2 回は app-only のみです (所見 7 のため)
- **A と B の別の書き方**
- **C が返す `RoleAssignments` が、Graph の権限エントリと同じ事実を表しているのかどうか。**
  数が近いのは測定であって、対応の証拠ではありません
- **1 回ずつの観測**です

> **誰を名指しするかはアプリが選びます。**

**これは所見 2 の続きです。** あのとき Azure RMS のトークンは**ロールを 1 つも持っていません
でした**。`Content.DelegatedReader` を付けたらそのロールが載り (所見 2 の追試)、**今回そのロールで
実際にコンテンツが開きました。** 「トークンが出る」→「ロールが載る」→「中身が開く」の 3 段が、

## 再現性

### `access` の 4 ファイル

**別々の日に、別々の実行環境から、同じ値が出ています。**

| | 実行環境 | A | B | C | D |
| --- | --- | --- | --- | --- | --- |
| 1 回目 | ファイルごとに個別実行 (GitHub ホストのランナー) | 4 / 0 | 5 / 0 | 5 / 0 | 3 / `404` |
| 2 回目 | **4 ファイルを 1 回の実行で** (GitHub ホストのランナー) | 4 / 0 | 5 / 0 | 5 / 0 | 3 / `404` |

さらに A については、**ローカルの開発機からの実行でも同じ 4 / 0** でした。

これは 1 つの留保を外します。GitHub ホストのランナーは送信元 IP もデバイスもローカルの開発機とは
違うので、そこで見えた拒否が「権限の所見」ではなく「条件付きアクセスがその条件で断った」だけである
可能性は常にあります (ワークフローのログはその旨を毎回表示します)。**この環境については、両方から
同じ値が出たことでその線が消えました** ― 環境側でも条件付きアクセス ポリシーが 0 件であることを
確認済みです ([environment.md](environment.md))。

一方、1 回の実行にまとめたことで **2 つの identity の答えの時間差が数百ミリ秒に縮まりました**。
所見 3 と 4 はどちらも「同じ対象を 2 つの identity で見比べる」ことでしか成り立たないので、その差が
「その間に何かが変わった」で説明できる余地は、実行を分けていたときより狭くなっています。

## 9 つを貫くもの

いずれも同じ間違いが違う衣装を着たものです。**手前の層が言っていることを、奥の層の事実として
扱うこと。**

| 受け取った答え | 素朴な読み | 実際に何だったか |
| --- | --- | --- |
| Azure RMS のトークンが発行された | このアプリは RMS に届く | 権限を 1 つも持たないトークン |
| SharePoint の委任アクセス許可は一覧にない | 利用者の代理では SharePoint に届かない | `Sites.Read.All` を持つ SharePoint 宛の委任トークン |
| 権限一覧が `200 OK` / 0 件 | このファイルは共有されていない | 見せてもらえないので空になった一覧 |
| アイテムが `404 itemNotFound` | このファイルは存在しない | 存在するが、この呼び出し元には見えない |
| app-only が `Sites.Read.All` を保持 | SharePoint REST を叩ける | Graph では叩けるが、`/_api/` では `401` |
| `401` なら権限を足せば通る | 強い権限なら通る | フル コントロールでも同じ `401` |
| 2 つの app-only トークンが同じロール・同じ `aud` | 同じように扱われる | 片方は `401`、片方は `200` ― 効いたのは名乗り方 (`appidacr` だけが違う) |
| フル コントロールでも `401` だった | この API は権限を見ない | 見ます ― ただし資格情報が通ったあとだけ |
| グループを一覧できた | メンバーも見られる | 一覧は 6 つ、中身が返るのは 3 つ |
| メンバーが `403` なのは閲覧者だから | アプリの identity なら見える | アプリでも `403` ― ただし権限を上げると `200` |
| メンバーが `403` | 見せてもらえない中身がある | 中身は 0 件だった |
| 束取りの経路が 2 つ拒否された | 権限が足りない | `notSupported` ― 権限の話ですらない |
| 束取りが 5 件、1 件ずつが 4 件 | 答えが食い違っている | 訊いた範囲が違う ― 片方は入れ子も歩く |
| 1 つのグループが `403` だった | グループの中身は見せてもらえない | 6 つ中 3 つは見える ― **測ったのが残りの 3 つ側だった** |
| RMS のトークンにロールが載った | このアプリは保護コンテンツを読める | 読めるのは**名指しした利用者が読めるもの**だけ |
| `Identity` と `DelegatedUserEmail` を両方設定した | 両方が認可に使われる | **使われるのは片方だけ** ― もう片方は空でなければ何でもよい |

層はこう並んでいます。

1. **アクセス許可の画面** ― 誰かが何を意図したか
2. **トークンのクレーム** ― Entra が実際に何を発行したか
3. **リソースの応答** ― そのリソースがそれをどう扱うか
4. **どの API を通ったか** ― 同じ権限・同じトークンでも答えが変わる
5. **どう名乗って取ったトークンか** ― クレームが同じでも答えが変わる
6. **渡した値のうち、どれが実際に読まれているか** ― 同じ呼び出しでも、効く値と効かない値がある

**この 6 つはどれも別物です。** ここに記録した実行では、隣り合う層がすべて食い違いました。
5 番目は**上の 4 つを全部そろえても、まだ答えが割れる**ことを示し、6 番目は**トークンより先、
呼び出しの中身にも同じ隙間がある**ことを示しています ― `Identity` は設定を要求されながら、
認可には一度も使われていませんでした。

そして所見 3・4・5・6 には共通の解き方があります。**同じ対象を、同じ瞬間に、複数の identity で
引くこと。** 片方だけを見ているかぎり、空も、`404` も、`401` も、事実に見えます。所見 5 の追試 3 は
**その 2 つを 3 つに増やしただけ**で、やり方は何も変わっていません ― そして、増やした 1 本が
所見 5 を解きました。

**もう 1 つ、同じ形の教訓があります。identity だけでなく、対象も 1 つに絞ると同じ穴が開きます。**
所見 6 は 6 つのグループのうち 1 つしか測っておらず、しかもその 1 つは誰も選んでいませんでした
(実装が先頭を取っていた)。**「一律に断られる」と「このグループだけ断られる」は、1 つしか訊いて
いないあいだ区別がつきません。** 全部に訊いた結果、所見の半分は測定の副産物でした。
**identity を並べるのと同じ理由で、対象も並べる必要があります。**

**断られ方は 3 種類あり、区別が要ります。**

| | 意味 |
| --- | --- |
| `401` | 認証されていない ― この経路でこの資格情報は受け付けられていない |
| `403` | 認証されている ― 操作が拒否された |
| `200` + 空 | 認証も認可も通った ― 中身が絞られた |

**下に行くほど静かで、下に行くほど誤読しやすくなります。**

所見 5 の追試 3 のあと、この 3 つは **1 つの identity の中に全部そろいます**。証明書で名乗った
app-only は、サイトを `200` で読み、あるグループの中身を `403` で断られます。同じアプリの
シークレット側は `401`。**「アプリが SharePoint に届くか」という問いには、少なくとも 3 つの
別々の答えがある**ということです。

そして追試 4 で、**この 3 つが順番に並んでいる**ことが見えました。`401` は資格情報の門、`403` は
その先の権限の門、`200` + 空はさらにその先の絞り込み。**手前の門で止まっているあいだ、奥の門の
状態は測れません** ― 追試 2 が「権限は変数ではない」に見えたのは、それが理由でした。

**さらに、同じ identity が同じ呼び出しで両方を受け取ります。** 証明書レグは `Sites.Read.All` の
まま、6 つのグループのうち 3 つに `200` を、3 つに `403` を返されます ― **1 本の呼び出しの
ステータスは、identity の性質でも API の性質でもなく、対象ごとの答え**でありうる、ということです。

## 再現するには

dotnet run --project src/CapabilityProbe.Cli -- auth
dotnet run --project src/CapabilityProbe.Cli -- access
dotnet run --project src/CapabilityProbe.Cli -- sharepoint
