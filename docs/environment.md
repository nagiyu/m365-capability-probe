# 検証環境

[docs/findings.md](findings.md) の観測が、どういう状態のテナントで取られたものかの記録。

所見は環境と切り離すと意味を失います。「委任側は権限一覧が 0 件だった」は、**そのアカウントがそのサイト
の閲覧者だった** という事実とセットでなければ何も言っていません。この文書はその「セット」のほうを保持
します。

**この文書は変わります。** 検証のためにファイルやアカウントを足すたびに更新し、所見のほうは
「どの版の環境で観測したか」を指します。差分が追えることがこの文書の役目なので、更新するときは
上書きではなく、末尾の「変更履歴」に何を足したかを書き残してください。

**識別子は書きません。** 公開リポジトリなので、テナント名・実アカウント名・サイト ID・アイテム ID は
入れず、役割で書きます。実物との対応が必要なら、それは git 管理外のローカル文書の役目です。

最終更新: 2026-08-04

## テナント

| 項目 | 値 |
| --- | --- |
| サブスクリプション | Microsoft 365 Business Premium (no Teams) ― 試用版 |
| 併せて | Microsoft Entra ID Free |
| クラウド | 商用 |
| 条件付きアクセス ポリシー | **0 件** |
| セキュリティの既定値群 | **有効** |

条件付きアクセスが 0 件でセキュリティの既定値群が有効、というのはこの環境について 2 つのことを
言っています。ひとつ、**同じアプリ・同じアカウントでも実行場所によって結果が変わる要因は、いまのところ
ありません。** GitHub Actions のランナーから実行した結果とローカルの結果が食い違ったら、条件付きアクセス
以外を疑うべきです (ワークフローのログにはその注意書きが入っていますが、この環境に限れば第一容疑者
ではありません)。ふたつ、**MFA は全利用者に強制されます。** デバイス コード フローはモダン認証なので
妨げられませんが、サインインの手数には効きます。

### 秘密度ラベル

**3 つ作成・公開済み。3 つとも「アクセスの制御」(保護) が設定されています。**

| ラベル | 使用権限 | 範囲 | コンテンツのマーキング | 自動ラベル付け |
| --- | --- | --- | --- | --- |
| `probe-viewonly` | View | ファイルと他のデータ資産, メール | なし | なし |
| `probe-print` | View + Print | 同上 | なし | なし |
| `probe-full` | View + DocEdit + Edit + Print + Export | 同上 | なし | なし |

**保護を適用するラベルだけが Azure Rights Management を使います。** 分類だけのラベルは RMS に触れず、
その場合「ラベルがある」ことは RMS について何も言いません。ここでは 3 つとも保護つきで、しかも
**マーキングも自動ラベル付けも無効** ― **このラベルは保護以外に何もしません。**

したがって **RMS はこのテナントで構成されています。** プロビジョニングされているだけの状態とは違い、
誰かが意図して使用権限を組んでいます。

**まだ測っていないこと**: **実際にラベルの付いたコンテンツがあるか。** 自動ラベル付けが無効なので
付与は手動で、どのファイルにもまだ付いていない可能性は残ります。「構成されている」と「使われている」
は別です。

**この節は一度、間違っていました。** 当初は「ラベルが公開済み」から「RMS が実際に動いている」を
断定し、その前提である「保護が設定されているか」を数行下の未記入に置いていました。上の表はその
未記入を埋めた結果です。

なお **所見 2 そのものはこれに依存しません。** Azure RMS のサービス プリンシパルがテナントに存在する
ことは、**測定そのものが証明しています** ― 存在しなければトークン要求は `AADSTS500011`
(リソースが見つからない) で拒否され、`aud: https://aadrm.com` を持つトークンは返りません。ラベルが
足すのは「存在する」ではなく「**構成されている**」のほうです。

## Entra: アプリ登録

アプリ登録は 1 つ。管理者の同意を与えたのは、正確に次のものだけです。

| API | アクセス許可 | 種類 | 管理者の同意 |
| --- | --- | --- | --- |
| Microsoft Graph | `Sites.Read.All` | アプリケーション | 済 |
| Microsoft Graph | `Sites.Read.All` | 委任 | 済 |
| Microsoft Graph | `User.Read` | 委任 | 済 (既定で付く) |
| SharePoint | `Sites.Read.All` | アプリケーション | 済 |

**SharePoint 側は一度だけ差し替えられ、戻されています。** 所見 5 の切り分けのために
`Sites.FullControl.All` (アプリケーション) へ差し替えて測定し、終了後に `Sites.Read.All` に戻しました
(変更履歴を参照)。**いまの状態は初版と同じ**です。

差し替えを残さなかったのは、**追跡可能性はこの変更履歴が担保するから**です。テナント内の全サイト
コレクションに対するフル コントロールを、シークレットが CI にあるアプリに持たせ続ける理由は
ありません。所見 5 の追試 2 が「その付与でどうなったか」を記録しているので、いま付与が無くても
測定結果は読めます。

Microsoft Graph 側は初版から一度も変えていません ― **対照として固定してあります**。

**意図的に付与していないもの** ― これらの欠落が測定対象です。

- **SharePoint の委任アクセス許可** (所見 1 の主題)
- **Azure Rights Management の一切** (所見 2 の主題)

### 構成

| 項目 | 値 |
| --- | --- |
| サポートされているアカウントの種類 | **この組織のディレクトリ内のアカウントのみ** (シングル テナント) |
| パブリック クライアント フローを許可する | **はい** (デバイス コード用) |
| リダイレクト URI | **登録なし** (デバイス コードには不要) |
| トークン構成 (オプションの要求) | **なし** |
| クライアント シークレット | あり。**app-only 側でのみ使用** |

デバイス コードはパブリック クライアント フローなので、委任側はシークレットを一切使いません。

シングル テナントであることは、所見 1 (Graph の委任同意が SharePoint に届く) を他所で再現するときの
前提になります。マルチテナント構成で同じことが起きるかは確認していません。

## Entra: アカウント

| 役割 | ユーザーの種類 | サイトに対する権限 | ディレクトリ ロール | ライセンス | グループ |
| --- | --- | --- | --- | --- | --- |
| 検証用の一般利用者 | メンバー | **閲覧者** グループのみ | **0 件** | 1 件 | 1 件 (セキュリティ グループ) |
| 操作者 | メンバー | 所有者 | 全体管理者 | 1 件 | ― |

検証用利用者は**ゲストではなくメンバー**で、ディレクトリ ロールを 1 つも持ちません。所見 3 の
「委任側 0 件」は、この状態のアカウントについての測定です。

所属している 1 つのグループは **クラウドのセキュリティ グループ** (割り当て済みメンバーシップ) で、
**Microsoft 365 グループではありません**。つまりこのサイトを支えるグループではなく、グループ経由で
サイトの権限が増えることもありません。閲覧者であるという記述は、そのまま成り立ちます。

委任側の実行は必ず検証用利用者で行います。操作者でサインインすると、測定対象がその管理者の到達範囲に
すり替わります。ツールは**実際にサインインした主体をレポートに記録する**ので、取り違えた実行は後から
判別できます。

## SharePoint

| 項目 | 値 |
| --- | --- |
| サイト | チーム サイト 1 つ (`https://<host>/sites/<name>`) |
| ライブラリ | 既定のドキュメント ライブラリのみ |
| ライブラリの表示名 | 「ドキュメント」 |
| ライブラリの内部名 | **`Shared Documents`** |

**表示名と内部名が違うことは、`FilePaths` の設定を間違える主な原因です。** URL には
`/sites/<name>/Shared Documents/...` と出るので、そのまま書きたくなりますが、パスはライブラリの
ルートを起点にするため、正しい値は `/test.docx` です。ライブラリ名を頭に付けると、ライブラリの中の
同名フォルダを探しに行って `404` になります (README の説明を参照)。

### サイトのグループ

| グループ | アクセス許可レベル |
| --- | --- |
| `<サイト名> 所有者` | フル コントロール |
| `<サイト名> メンバー` | 編集 |
| `<サイト名> 閲覧者` | 閲覧 |

上の 3 つが、サイトを作ったときの既定の構成です。**所見 1〜4 はこの状態で観測しました。**

**この 3 つが所見 3 の「4 件」を説明します。** app-only で読んだ権限エントリは 4 件、現れたプリンシパル
の種類は `sharePointGroup` / `siteGroup` / `siteUser` / `user` の 4 種類でした。Graph の権限エントリは
1 件で複数の種類を持ちうるので ― SharePoint グループのエントリは `siteGroup` と `sharePointGroup` の
両方を、ユーザーのエントリは `user` と `siteUser` の両方を持ちます ― **3 つのグループ + ユーザー 1 名
= 4 件** と整合します。

ただしこれは件数と種類からの推測です。**ツールは個々のエントリの中身を記録していない** ので、4 件目の
ユーザーが誰かは分かりません ― **推測すらしていません**。サイト作成者だろうという当てはありますが、
それを支える測定はありません。

#### その後 ― 測定が環境を変えた

**2026-08-04 に SharePoint REST でグループを一覧したところ、6 つ**ありました。増えた分は
`Limited Access System Group For List <GUID>` という名前です。

**ここから先は推測です。** 名前からすると SharePoint が自動生成したもので、所見 4 のために
`restricted` フォルダの継承を切ったことが原因と見られます。ただし **この種のグループがいつ作られるかは
調べていませんし、作られた時刻も記録していません。** 測定として言えるのは、**当初 3 つだったものが
6 つになっていた**ことだけです。

推測が当たっているなら、**所見 4 のための環境変更が、あとから所見 6 の観測対象を変えていた**ことに
なります。いずれにせよ所見 3 の「4 件」は 3 つだった時点の測定で、いま同じ測定をすれば違う数字が出る
可能性があります。

**この文書が変更履歴を持っている理由がこれです。** 所見のほうは「どの版の環境で観測したか」を指します。

### ファイル

共有状態の違う 4 つ。**すべて既定のドキュメント ライブラリの中**にあります ― `access` は
`/drive/root:` を起点にし、そこは既定のライブラリ 1 つだけを指すので、別のライブラリに置くと
app-only ですら到達できず、比較になりません。

| # | ファイル | 場所 | 共有状態 | 観測された権限エントリ数 (app-only) |
| --- | --- | --- | --- | --- |
| A | `test.docx` | ライブラリ直下 | 継承のみ | 4 |
| B | `b-direct.docx` | ライブラリ直下 | **検証用利用者本人に直接アクセス許可** (表示可能) | 5 |
| C | `c link share.docx` | ライブラリ直下 | **組織内リンク** で共有 | 5 (`link:organization` を含む) |
| D | `d-restricted.docx` | `restricted/` フォルダ内 | フォルダで**継承を中止し、閲覧者グループを削除** | 3 |

件数は互いに整合しています。A の 4 件を基準に、付与を 1 つ足した B と C は 1 件ずつ多く、閲覧者
グループを外した D は 1 件少ない。**どのエントリが増減したかは記録していない** ので、対応づけ自体は
推測ですが、4 ファイルの数がすべて操作と同じ向きに動いていることは測定です。

C の名前に**半角スペースが入っている**のは意図的で、URL エスケープ (`%20`) が実際の要求で効くことを
確認するためです。この 1 件で確認できています。

D の `restricted/` フォルダは、**検証用利用者からは存在自体が見えません**。

## この環境で取った観測

| 所見 | 依存している環境の要素 |
| --- | --- |
| 1. Graph の委任同意が SharePoint に届く | Graph 委任 `Sites.Read.All` が同意済み / SharePoint 委任が未付与 / シングル テナント |
| 2. app-only は空のトークンを発行される | Azure RMS が未付与 / RMS のサービス プリンシパルがテナントに存在する (測定そのものが示す) / 保護つきの秘密度ラベルが 3 つ構成されている |
| 3. 権限一覧は 403 ではなく 200 / 0 件 | 委任アカウントがサイトの **閲覧者**、ディレクトリ ロールなし / ファイル A・B・C の 3 通りの共有状態で確認 |
| 4. 見えないファイルは 404 itemNotFound | ファイル D のフォルダで継承を中止し、閲覧者グループを削除している |
| 5. app-only は SharePoint REST に 401、委任は 200 | SharePoint のアプリケーション付与が `Sites.Read.All` でも `Sites.FullControl.All` でも同じ / SharePoint の**委任**は未付与 |
| 6. グループは一覧できるが中身は 403 | 委任アカウントがサイトの **閲覧者** / 対象は ID の若いグループ 1 つ |

所見 3 は特に、閲覧者という役割に強く依存しています。メンバーや所有者で同じ測定をすると別の数字が
出るかもしれませんが、**確認していません**。**共有状態への依存は無い** ことは、A・B・C の 3 通りで
確認済みです。
