# 検証環境

[docs/findings.md](findings.md) の観測が、どういう状態のテナントで取られたものかの記録。

所見は環境と切り離すと意味を失います。「委任側は権限一覧が 0 件だった」は、**そのアカウントがそのサイト
の閲覧者だった** という事実とセットでなければ何も言っていません。この文書はその「セット」のほうを保持
します。

**この文書は変わります。** 検証のためにファイルやアカウントを足すたびに更新し、所見のほうは
「どの版の環境で観測したか」を指します。差分が追えることがこの文書の役目なので、更新するときは
上書きではなく、末尾の「変更履歴」に何を足したかを書き残してください。

**識別子は書きません。** 公開リポジトリなので、テナント名・実アカウント名・サイト ID・アイテム ID は
入れず、役割で書きます。実物との対応が必要なら、それは git 管理外のローカル文書の役目です。

### 秘密度ラベル

**5 つ作成・公開済み。5 つとも「アクセスの制御」(保護) が設定されています。**

| ラベル | 使用権限 | 範囲 | コンテンツのマーキング | 自動ラベル付け |
| --- | --- | --- | --- | --- |
| `probe-viewonly` | View | ファイルと他のデータ資産, メール | なし | なし |
| `probe-print` | View + Print | 同上 | なし | なし |
| `probe-full` | View + DocEdit + Edit + Print + Export | 同上 | なし | なし |
| **`probe-miku-only`** | **ミク 1 人だけに付与** (リンは対象外) | ファイル | なし | なし |
| **`probe-userdefined`** | **テンプレートを使わず、適用した人が権利の相手を選ぶ** | ファイル | なし | なし |

**`probe-miku-only` は所見 9 のために作ったものです。** 他の 3 つと違い、**誰に与えるかのほうが
測定の中身**です ― 「権利を持たない実在の利用者」を 1 人作るために、**リンを外して**あります。

**`probe-userdefined` は「テンプレート以外の形」を作るためのものです。** 上の 4 つがテンプレートに
権利を書いてあるのに対し、これは**適用の瞬間に人が相手を選びます**。保護の記述がどう変わるのかを
測るためのものです。**リンがこれでファイル G を保護し、権利の相手にルカ 1 人を指定しました** ―
`consume` はこの保護を **`Custom`** と報告します (所見 10)。

**保護を適用するラベルだけが Azure Rights Management を使います。** 分類だけのラベルは RMS に触れず、
その場合「ラベルがある」ことは RMS について何も言いません。ここでは 5 つとも保護つきで、しかも
**マーキングも自動ラベル付けも無効** ― **このラベルは保護以外に何もしません。**

したがって **RMS はこのテナントで構成されています。** プロビジョニングされているだけの状態とは違い、
誰かが意図して使用権限を組んでいます。

**まだ測っていないこと**: **実際にラベルの付いたコンテンツがあるか。** 自動ラベル付けが無効なので
付与は手動で、どのファイルにもまだ付いていない可能性は残ります。「構成されている」と「使われている」
は別です。

**この節は一度、間違っていました。** 当初は「ラベルが公開済み」から「RMS が実際に動いている」を
断定し、その前提である「保護が設定されているか」を数行下の未記入に置いていました。上の表はその
未記入を埋めた結果です。

なお **所見 2 そのものはこれに依存しません。** Azure RMS のサービス プリンシパルがテナントに存在する
ことは、**測定そのものが証明しています** ― 存在しなければトークン要求は `AADSTS500011`
(リソースが見つからない) で拒否され、`aud: https://aadrm.com` を持つトークンは返りません。ラベルが
足すのは「存在する」ではなく「**構成されている**」のほうです。

#### RMS 側から見たテンプレート (2026-08-04)

上の表はラベルの管理画面から書いたものです。**同じことを RMS 側から読むと、こうなります** ―
`Connect-AipService` のあと `Get-AipServiceTemplateProperty -RightsDefinitions`。

| テンプレート | 付与先 (`Identity`) | 権利 (`Rights`) |
| --- | --- | --- |
| `probe-viewonly` | `<検証用利用者の UPN>` | `VIEW, VIEWRIGHTSDATA` |
| `probe-print` | 同上 | `VIEW, VIEWRIGHTSDATA, PRINT` |
| `probe-full` | 同上 | `VIEW, VIEWRIGHTSDATA, DOCEDIT, EDIT, PRINT, EXPORT` |
| 社外秘 \ すべての従業員 **(既定)** | `AllStaff-<GUID>@<テナント>` | `VIEW, EXTRACT, OBJMODEL, VIEWRIGHTSDATA, PRINT, FORWARD, REPLY, REPLYALL, EDIT, DOCEDIT, EDITRIGHTSDATA, OWNER, EXPORT` |

**2 つの経路が一致しました。** 管理画面で見た使用権限と、RMS のテンプレートが持つ権利は、
3 つとも同じものを指しています ― `View` = `VIEW`、`View + Print` = `VIEW, PRINT`、
`View + DocEdit + Edit + Print + Export` = `VIEW, DOCEDIT, EDIT, PRINT, EXPORT`。
**この文書でこれまで書いてきた使用権限は、別の経路から確かめられたことになります。**

**付与先は特定のユーザー 1 名です** ― 全従業員でも、グループでもありません。既定の 2 つが
`AllStaff-<GUID>` という動的グループを指しているのと対照的で、**どれが自分で作ったものかは
付与先を見れば分かります**。

**`VIEWRIGHTSDATA` は 3 つすべてに付いていますが、管理画面で設定した覚えのない権利です。**
何が足しているのかは測っていません。既定の 2 つは 13 個の権利を持ち、そこには `OWNER` も
含まれます。

**名前のとおりなら「その内容にどんな権利が設定されているかを見る」権利**です (対になるのが
`EDITRIGHTSDATA`)。**これは権限名の語彙についての説明で、測定ではありません。**

**測ったのは 1 つだけ** ― この権利を持つ相手 (ミク) が `probe-rin-protected.docx` を開いても、
`consume` の `named in the policy` は **`(none listed)`** でした (所見 10 の訂正)。
**名前が指すものと、SDK の `ProtectionDescriptor` を埋める規則が同じかどうかは切り分けていません。**

**Word のアクセス許可ダイアログからは、この権利だけを与えることができません** ―
閲覧者 / 制限付きエディター / エディター / オーナーの 4 段階しかなく、「その他のオプション」も
有効期限・追加許可の要求先・プログラムからのアクセス・接続の要求の 4 項目だけです。

**まだ測っていないこと**: **この権利が実際に効くかどうか。** これは「テンプレートにこう書いてある」
という記録で、保護されたファイルを開いて確かめたわけではありません。

##### この経路で読めるか

狙いは「付与先がコマンドで読める形で返るか」でした。**返ります** ― `Identity` に UPN が、
`Rights` に権利名の配列がそのまま入ります。ただし途中に 3 つ引っかかりがありました。

- **`Get-AipServiceTemplate` は権利も付与先も返しません。** ID と名前と説明だけで、
  `Get-AipServiceTemplateProperty` を別に叩く必要があります
- **一覧の出力はパイプラインで素直に回りません。** 5 件が 1 つの配列として出るので、
  `ForEach-Object` に流すと `$_.TemplateId` が GUID 5 個の配列になり、次のコマンドの型変換で
  落ちます。ID を直接渡すのが確実です
- **既定の表示は権利を切ります。** `{VIEW, VIEWRIGHTSDATA, DOCEDIT, EDIT...}` の `...` が
  そうで、**そのまま読むと `probe-full` の権利を 4 つだと取り違えます**。`$_.Rights -join ', '`
  で展開すれば 6 つ出ます

3 つ目は、この道具が同じ日に自分でやった間違いと同じ形です (所見 8 のコードへの反映)。
**表示の都合で切られた答えは、短い答えに見えます。**

##### スーパーユーザーの登録は、足すときと外すときで形が違います

所見 11 の測定中に引っかかった点です。

- **`Add-AipServiceSuperUser` には `-ServicePrincipalId` があり、GUID で足せます**
- **`Remove-AipServiceSuperUser` には `-ServicePrincipalId` がありません** ― `-EmailAddress` だけです
- 渡す値は `Get-AipServiceSuperUser` が返す文字列そのもので、
  **`<クライアント ID>@<テナント ID>.rms.<リージョン>.aadrm.com`** の形をしています

**リージョンまで入っています** ― こちらが指定した覚えのない情報です。**入れた値と一覧に出る値が違うので、
`Get-AipServiceSuperUser` の出力を控えずに足すと、外し方が分からなくなります。**

なお、最初に `Get-AipServiceTemplate` を叩いたとき、`probe-*` の 3 つは
**`No name defined in ja-JP`** と出ました。既定の 2 つが 30 以上のロケールで名前を持つのに対し、
`probe-*` は**名前を 1 つしか持たない**ためです。**一覧だけでは、どれがどのラベルかも分かりません。**

### 構成

| 項目 | 値 |
| --- | --- |
| サポートされているアカウントの種類 | **この組織のディレクトリ内のアカウントのみ** (シングル テナント) |

| クライアント シークレット | あり。**app-only (シークレット) 側でのみ使用** |

デバイス コードはパブリック クライアント フローなので、委任側はどちらの資格情報も使いません。

**証明書を足してもアクセス許可は 1 つも変わっていません。** 増えたのは、同じアプリが自分を証明する
方法の選択肢だけです。この 2 つを同じ実行の中で並べたのが所見 5 の追試 3 で、**`/_api/` の答えが
シークレットでは `401`、証明書では `200` に分かれました**。

登録したのは公開鍵 (`.crt`) だけで、秘密鍵はテナントに渡っていません。`.pfx` は base64 にして
`PROBE_CLIENTCERTIFICATE` シークレットに置いてあり、実行時にランナーの一時ファイルへ書き出されます。

シングル テナントであることは、所見 1 (Graph の委任同意が SharePoint に届く) を他所で再現するときの
前提になります。マルチテナント構成で同じことが起きるかは確認していません。

います ― 保護の所有者は**適用の瞬間に刻まれる**ので、それで足ります。閲覧者グループに入れると
**所見 6 が測っているグループ構成そのものが動く**ため、避けました。

**ルカは「UPN とメールのローカル部が違う利用者」です** ― UPN が `luka@`、主メール アドレスが
`luka-mail@`（Exchange で主 SMTP を差し替え）。`DelegatedUserEmail` に入れる**値の形**が認可に効くのか
を測るためのものです。**ルカも一度もサインインしていません** ― ファイル G の権利の相手として
リンに名指しされただけで、**それで足りました** (所見 10)。

検証用利用者は**ゲストではなくメンバー**で、ディレクトリ ロールを 1 つも持ちません。所見 3 の
「委任側 0 件」は、この状態のアカウントについての測定です。

所属している 1 つのグループは **クラウドのセキュリティ グループ** (割り当て済みメンバーシップ) で、
**Microsoft 365 グループではありません**。つまりこのサイトを支えるグループではなく、グループ経由で
サイトの権限が増えることもありません。閲覧者であるという記述は、そのまま成り立ちます。

委任側の実行は必ず検証用利用者で行います。操作者でサインインすると、測定対象がその管理者の到達範囲に
すり替わります。ツールは**実際にサインインした主体をレポートに記録する**ので、取り違えた実行は後から
判別できます。

### Entra のグループ

| 名前 | 種類 | メンバー | 何のために |
| --- | --- | --- | --- |
| `probe-group` | セキュリティ (割り当て済み) | ミク | 元からあるもの。所見 3 の「グループ経由で権限が増えない」の対象 |
| **`probe-cycle-a`** | セキュリティ (割り当て済み) | `probe-cycle-b` | **所見 13** |

**`probe-cycle-a` と `probe-cycle-b` は互いを相手のメンバーにしてあります** ― 輪が閉じています。
**ポータルはこの操作を止めませんでした** (警告も確認も出ません)。

**この 2 つは SharePoint のサイトにも秘密度ラベルにも紐付いていません。** 他の所見の基準を動かさない
ように、Entra の中だけで閉じています。**ミクが直接入っているのは意図的**で、人がいないと
`transitiveMembers` が空でも「輪のせい」か「そもそも誰もいない」かが区別できません。

**残してあります。** 消すと所見 13 が再現できなくなるので、**戻す測定 (同意の取り消し) と一緒に
判断する**ことにしています。

## SharePoint

| 項目 | 値 |
| --- | --- |
| サイト | チーム サイト 1 つ (`https://<host>/sites/<name>`) |
| ライブラリ | 既定のドキュメント ライブラリのみ |
| ライブラリの表示名 | 「ドキュメント」 |
| ライブラリの内部名 | **`Shared Documents`** |

**表示名と内部名が違うことは、`FilePaths` の設定を間違える主な原因です。** URL には
`/sites/<name>/Shared Documents/...` と出るので、そのまま書きたくなりますが、パスはライブラリの
ルートを起点にするため、正しい値は `/test.docx` です。ライブラリ名を頭に付けると、ライブラリの中の
同名フォルダを探しに行って `404` になります (README の説明を参照)。

### サイトのグループ

| グループ | アクセス許可レベル |
| --- | --- |
| `<サイト名> 所有者` | フル コントロール |
| `<サイト名> メンバー` | 編集 |
| `<サイト名> 閲覧者` | 閲覧 |

上の 3 つが、サイトを作ったときの既定の構成です。**所見 1〜4 はこの状態で観測しました。**

**この 3 つが所見 3 の「4 件」を説明します。** app-only で読んだ権限エントリは 4 件、現れたプリンシパル
の種類は `sharePointGroup` / `siteGroup` / `siteUser` / `user` の 4 種類でした。Graph の権限エントリは
1 件で複数の種類を持ちうるので ― SharePoint グループのエントリは `siteGroup` と `sharePointGroup` の
両方を、ユーザーのエントリは `user` と `siteUser` の両方を持ちます ― **3 つのグループ + ユーザー 1 名
= 4 件** と整合します。

ただしこれは件数と種類からの推測です。**ツールは個々のエントリの中身を記録していない** ので、4 件目の
ユーザーが誰かは分かりません ― **推測すらしていません**。サイト作成者だろうという当てはありますが、
それを支える測定はありません。

**上の内訳**だけです。

なります。いずれにせよ所見 3 の「4 件」は 3 つだった時点の測定で、いま同じ測定をすれば違う数字が出る
可能性があります。

**この文書が変更履歴を持っている理由がこれです。** 所見のほうは「どの版の環境で観測したか」を指します。
