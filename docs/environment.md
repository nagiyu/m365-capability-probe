# 検証環境

[docs/findings.md](findings.md) の観測が、どういう状態のテナントで取られたものかの記録。

所見は環境と切り離すと意味を失います。「委任側は権限一覧が 0 件だった」は、**そのアカウントがそのサイト
の閲覧者だった** という事実とセットでなければ何も言っていません。この文書はその「セット」のほうを保持
します。

**この文書は変わります。** 検証のためにファイルやアカウントを足すたびに更新し、所見のほうは
「どの版の環境で観測したか」を指します。差分が追えることがこの文書の役目なので、更新するときは
上書きではなく、末尾の「変更履歴」に何を足したかを書き残してください。

**識別子は書きません。** 公開リポジトリなので、テナント名・実アカウント名・サイト ID・アイテム ID は
入れず、役割で書きます。実物との対応が必要なら、それは git 管理外のローカル文書の役目です。

## テナント

| 項目 | 値 |
| --- | --- |
| サブスクリプション | Microsoft 365 Business Premium (no Teams) ― 試用版 |
| 併せて | Microsoft Entra ID Free |
| クラウド | 商用 |
| 条件付きアクセス ポリシー | **0 件** |
| セキュリティの既定値群 | **有効** |

条件付きアクセスが 0 件でセキュリティの既定値群が有効、というのはこの環境について 2 つのことを
言っています。ひとつ、**同じアプリ・同じアカウントでも実行場所によって結果が変わる要因は、いまのところ
ありません。** GitHub Actions のランナーから実行した結果とローカルの結果が食い違ったら、条件付きアクセス
以外を疑うべきです (ワークフローのログにはその注意書きが入っていますが、この環境に限れば第一容疑者
ではありません)。ふたつ、**MFA は全利用者に強制されます。** デバイス コード フローはモダン認証なので
妨げられませんが、サインインの手数には効きます。

### 秘密度ラベル

**3 つ作成・公開済み** (`probe-full` / `probe-print` / `probe-viewonly` の 3 段階)。

**これは所見 2 にとって重要です。** 所見 2 は「Azure RMS のサービス プリンシパルがテナントに存在する
から、権限が 0 個でもトークンが発行される」と説明していますが、当初その存在は推測でした。秘密度ラベル
が公開されているということは、**RMS はこのテナントで実際に動いています。** つまりあの空のトークンは、
存在しないサービス宛に出た無害なものではなく、**生きているサービス宛に発行された、何もできない
トークン** です。

(Business Premium は通常 Azure Information Protection P1 を含むので SKU の面からも辻褄は合いますが、
直接の証拠はラベルが公開されている事実のほうです。)

## Entra: アプリ登録

アプリ登録は 1 つ。管理者の同意を与えたのは、正確に次のものだけです。

| API | アクセス許可 | 種類 | 管理者の同意 |
| --- | --- | --- | --- |
| Microsoft Graph | `Sites.Read.All` | アプリケーション | 済 |
| Microsoft Graph | `Sites.Read.All` | 委任 | 済 |
| Microsoft Graph | `User.Read` | 委任 | 済 (既定で付く) |
| SharePoint | `Sites.Read.All` | アプリケーション | 済 |

**意図的に付与していないもの** ― これらの欠落が測定対象です。

- **SharePoint の委任アクセス許可** (所見 1 の主題)
- **Azure Rights Management の一切** (所見 2 の主題)

### 構成

| 項目 | 値 |
| --- | --- |
| サポートされているアカウントの種類 | **この組織のディレクトリ内のアカウントのみ** (シングル テナント) |
| パブリック クライアント フローを許可する | **はい** (デバイス コード用) |
| リダイレクト URI | **登録なし** (デバイス コードには不要) |
| トークン構成 (オプションの要求) | **なし** |
| クライアント シークレット | あり。**app-only 側でのみ使用** |

デバイス コードはパブリック クライアント フローなので、委任側はシークレットを一切使いません。

シングル テナントであることは、所見 1 (Graph の委任同意が SharePoint に届く) を他所で再現するときの
前提になります。マルチテナント構成で同じことが起きるかは確認していません。

## Entra: アカウント

| 役割 | ユーザーの種類 | サイトに対する権限 | ディレクトリ ロール | ライセンス | グループ |
| --- | --- | --- | --- | --- | --- |
| 検証用の一般利用者 | メンバー | **閲覧者** グループのみ | **0 件** | 1 件 | 1 件 (未確認) |
| 操作者 | メンバー | 所有者 | 全体管理者 | 1 件 | ― |

検証用利用者は**ゲストではなくメンバー**で、ディレクトリ ロールを 1 つも持ちません。所見 3 の
「委任側 0 件」は、この状態のアカウントについての測定です。

委任側の実行は必ず検証用利用者で行います。操作者でサインインすると、測定対象がその管理者の到達範囲に
すり替わります。ツールは**実際にサインインした主体をレポートに記録する**ので、取り違えた実行は後から
判別できます。

## SharePoint

| 項目 | 値 |
| --- | --- |
| サイト | チーム サイト 1 つ (`https://<host>/sites/<name>`) |
| ライブラリ | 既定のドキュメント ライブラリのみ |
| ライブラリの表示名 | 「ドキュメント」 |
| ライブラリの内部名 | **`Shared Documents`** |

**表示名と内部名が違うことは、`FilePath` の設定を間違える主な原因です。** URL には
`/sites/<name>/Shared Documents/...` と出るので、そのまま `FilePath` に書きたくなりますが、
`FilePath` はライブラリのルートを起点にするため、正しい値は `/test.docx` です。ライブラリ名を頭に
付けると、ライブラリの中の同名フォルダを探しに行って `404` になります (README の説明を参照)。

### サイトのグループ

| グループ | アクセス許可レベル |
| --- | --- |
| `<サイト名> 所有者` | フル コントロール |
| `<サイト名> メンバー` | 編集 |
| `<サイト名> 閲覧者` | 閲覧 |

既定の 3 つ。追加のグループも、個別に権限を与えられたユーザーもありません。

**この 3 つが所見 3 の「4 件」を説明します。** app-only で読んだ権限エントリは 4 件、現れたプリンシパル
の種類は `sharePointGroup` / `siteGroup` / `siteUser` / `user` の 4 種類でした。Graph の権限エントリは
1 件で複数の種類を持ちうるので ― SharePoint グループのエントリは `siteGroup` と `sharePointGroup` の
両方を、ユーザーのエントリは `user` と `siteUser` の両方を持ちます ― **3 つのグループ + ユーザー 1 名
= 4 件** と整合します。

ただしこれは件数と種類からの推測です。**ツールは個々のエントリの中身を記録していない** ので、4 件目の
ユーザーが誰かは分かりません (サイト作成者と見られます)。

## この環境で取った観測

| 所見 | 依存している環境の要素 |
| --- | --- |
| 1. Graph の委任同意が SharePoint に届く | Graph 委任 `Sites.Read.All` が同意済み / SharePoint 委任が未付与 / シングル テナント |
| 2. app-only は空のトークンを発行される | Azure RMS が未付与 / **秘密度ラベルが公開済みで RMS が実際に動いている** |
| 3. 権限一覧は 403 ではなく 200 / 0 件 | 委任アカウントがサイトの **閲覧者**、ディレクトリ ロールなし / 対象ファイルに 4 件のエントリ |

所見 3 は特に、閲覧者という役割に強く依存しています。メンバーや所有者で同じ測定をすると別の数字が
出るはずで、それはまだ確認していません。
